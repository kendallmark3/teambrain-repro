Section 01

What Is Intent-Driven Development?

Before you touch a single file in the repository, you need to understand the core mental shift. Intent-driven development is not about learning a framework — it is about changing how you think before you write a single line of code.

The Old Way vs. The Intent Way

The Old WayThe Intent Way
Start by opening your IDEStart by writing what you want in plain language
Write code, then figure out structureWrite the outcome, then let structure emerge from it
Design and implementation are separate documentsIntent IS the design — code is generated from it
Specs drift from code over timeIntent stays in sync — it IS the source of truth
Ramp-up = learning the codebaseRamp-up = learning to describe outcomes precisely

The One-Line Principle

Every file in the teambrain-repro repository follows a single principle:

"Describe what you want once → everything else aligns automatically."

This means:

  • Intent files are not documentation — they are source code for your system
  • Claude is not a tool you use — it is the execution engine
  • Your job shifts from writing code to writing precise intent
  • Governance, architecture, security, and testing are all defined as intent — not enforced manually
💡 Why This Changes Everything for Teams

Traditional teams spend enormous energy on alignment: sprint planning, PRD reviews, architecture reviews, code reviews. Intent-driven teams encode alignment directly into the system. When intent is clear, Claude generates consistent, standards-compliant code — every time.

Section 03

How Claude Works in This System

Many teams make the mistake of treating Claude like a search engine or smarter autocomplete. In the TeamBrain system, Claude plays three distinct roles.

Claude's Three Roles

RoleWhat Claude Is DoingDriven By
GeneratorTaking a declarative intent file and producing code, APIs, or UI componentsintentapi.md, intentdice.md
EnforcerValidating that intent is complete and clear before any generation beginsintent-check.md
AgentOperating autonomously across multiple tasks, maintaining context, running workflowsteambrain-agent/intent.md

The Generation Loop

Every interaction with Claude in this system follows the same loop. Burn this into your team's muscle memory:

① Write Intent → ② Run Intent-Check → ③ Feed to Claude → ④ Review Output → ⑤ Refine Intent
Repeat until output matches intent. The intent file — not the generated code — is what you version-control.

What Claude Needs to Generate Good Code

Claude performs best when intent files are specific on four dimensions:

DimensionPoor IntentStrong Intent
Purpose"Build an API""Build a RESTful customer management API with CRUD operations, JWT auth, and Node.js"
Constraints(none stated)"Follow the architecture.intent.md standards — layered controller/service pattern"
Technology"Use modern tools""Node.js 20, Express 4, PostgreSQL, deployed via the devops.intent.md pipeline"
Acceptance"Make it work""All endpoints return standard error shapes; 90% test coverage per testing.intent.md"

The YAML Intent Format

Some files use YAML for machine-readable intent — useful for agent workflows:

intent: Payment Authorization API
version: 1.0
owner: payments-team

purpose: Authorize payment transactions with fraud detection

constraints:
  - follows: architecture.intent.md
  - follows: security.intent.md
  - follows: testing.intent.md

technology:
  runtime: Node.js 20
  framework: Express
  database: PostgreSQL

acceptance:
  - All transactions logged with correlation IDs
  - 95%+ test coverage
  - PCI-DSS compliant error handling
💡 Key Insight: Intent Inheritance

Notice the follows keys above. This is intent inheritance — the payment API does not redefine security or architecture rules. It references system-level intents and inherits all their standards. This is how TeamBrain ensures consistency across all generated code without repeating constraints in every intent file.

Section 04

The 4-Phase Learning Journey

This is the recommended onboarding path for any new team member. Do not skip phases — each one builds on the mental models of the previous one. Estimated total time: 2–3 weeks.

1
Read & Orient — Days 1–2
Understand the system before you touch anything
2
Run a Demo — Days 3–5
See the system produce real output end-to-end
3
Write an Intent — Days 6–10
Author your first intent file from scratch
4
Contribute & Systematize — Days 11–15
Extend the system and establish team patterns

Phase 1 — Read & Orient

  • Clone the repo and read TableOfContents.md in full
  • Read the six intent files in the recommended reading order — do not generate code yet
  • For each file, write a 1-sentence answer: "What outcome does this intent produce?"
  • Map the files mentally to the L1–L6 layers
✅ Exit Criteria

You can explain the difference between an Execution Intent and a System Intent. You can explain why intent-check.md is the most important file. You can describe the Generation Loop in your own words.

Phase 2 — Run a Demo

  • Open intentdemo/intent.md and read it carefully
  • Run intent-check.md against it — does the intent pass all governance checks?
  • Feed the intent to Claude exactly as written — no modifications
  • Review the output: does it match the intent?
  • Modify one thing in the intent and re-run — observe how output changes
  • Repeat with intentdice.md (UI) and intentapi.md (backend)
✅ Exit Criteria

You have run at least 3 intent files through Claude. You have intentionally broken an intent and observed Claude struggling. You understand that intent specificity directly controls output quality.

Phase 3 — Write an Intent

  • Pick a small, real task from your current work
  • Write the intent file in Markdown — do not open your IDE yet
  • Run your intent through intent-check.md — answer every governance question
  • Feed it to Claude and evaluate the output against your intent
  • Refine the intent (not the code) until the output is correct
⚠️ Common Mistake at Phase 3

New team members often start fixing the generated code directly when it is wrong. Do not do this. If the output is wrong, the intent is wrong. Go back and fix the intent. This discipline is what separates intent-driven teams from teams that just use AI as autocomplete.

✅ Exit Criteria

You have authored one intent file that produces correct, standards-compliant output. You have not manually edited any generated code. Your intent references the appropriate system intents.

Phase 4 — Contribute & Systematize

  • Use intent-driven development for your next real feature or task
  • If a system intent is missing, write one and submit it as a PR
  • Review a teammate's intent file the way you would review code
  • Explore teambrain-agent/intent.md to understand autonomous agent intents
✅ Exit Criteria

You have used intent-driven development on a real production task. You have reviewed at least one colleague's intent file. You can explain the difference between a one-shot intent and an agent intent.

Section 05

Team Practices & Operating Rules

The Five Non-Negotiables

1
Intent before code — always
If there is no intent file, there is no work. This prevents scope creep and misalignment.
2
Fix intent, not output
Editing generated code directly is technical debt disguised as productivity. The intent is the source of truth.
3
Intent-check is mandatory, not optional
Skipping intent-check is like skipping code review. Governance exists for a reason.
4
System intents are team contracts
architecture.intent.md, security.intent.md, etc. are binding. No execution intent overrides them.
5
Intent files live in version control
Intent is code. It gets committed, reviewed, and versioned exactly like source files.

Sprint Workflow Integration

Sprint EventIntent-Driven Practice
Sprint PlanningFor each story, write a draft intent file. If you cannot write an intent, the story is not ready.
RefinementRun intent-check.md on each intent. Resolve ambiguities before the sprint starts.
DevelopmentFeed intent to Claude, review output, refine intent, repeat. No manual code editing.
Code ReviewReview the intent file, not just the generated code. Does the intent reflect what was built?
RetrospectiveWhich intents were hard to write? Which system intents need updating?

Intent Review Checklist

  • Is the purpose stated in one clear sentence?
  • Are all technology choices explicit (language, framework, version)?
  • Are the appropriate system intents referenced?
  • Are acceptance criteria defined — how will you know the output is correct?
  • Are there any ambiguous terms Claude could interpret multiple ways?
  • Does the scope feel right — not too large for one generation cycle?
  • Has intent-check.md been run and passed?

When Intent-Driven Development Is Hard

SituationWhat To Do
"I don't know what I want yet"Write an exploratory intent. Ask Claude to help you discover options. Discovery is valid intent.
"It's a tiny change — 5 lines"Still write intent. Even small changes should be traceable. It takes 2 minutes.
"The generated code is almost right but has one bug"Fix the intent, not the bug. Add a constraint like "must handle null values in X field".
"Claude keeps misunderstanding me"Your intent is ambiguous. Add an example (input/output pair) to the intent file.
"We don't have a system intent for this domain"Write one. This is a contribution to the team — not a blocker.

Quick Reference

Intent File Anatomy

# Intent: [Name of the thing you want to build]

## Purpose
[One sentence: what does this produce and why does it exist?]

## Technology
- Runtime: [e.g., Node.js 20]
- Framework: [e.g., Express 4]
- Database: [e.g., PostgreSQL 15]

## Constraints
- Follows: architecture.intent.md
- Follows: security.intent.md
- Follows: testing.intent.md

## Behavior
[Describe what the system does. Be specific. Use examples if helpful.]

## Acceptance Criteria
- [Criterion 1: measurable, specific]
- [Criterion 2: measurable, specific]

Glossary

TermDefinition
Intent FileA Markdown or YAML file that declaratively describes the desired outcome of a system or component.
Execution IntentAn intent that produces a concrete artifact — code, API, UI, or feature.
System IntentAn intent that defines standards and constraints applied across all execution intents.
Agent IntentAn intent that defines autonomous, multi-step behavior for an AI agent.
Governance IntentAn intent that validates other intents before execution begins.
Intent InheritanceWhen an execution intent references a system intent using "follows:", inheriting all its constraints.
Intent-CheckThe governance validation step that must pass before Claude generates any output.
Generation LoopWrite Intent → Intent-Check → Feed to Claude → Review → Refine Intent. Repeat.

The Meta-Intent Layer (Advanced)

The next evolution is a meta-intent layer — a single file that composes all system intents into a unified enterprise blueprint:

intent: Build Enterprise System
includes:
  - architecture.intent.md
  - security.intent.md
  - devops.intent.md
  - frontend.intent.md
  - testing.intent.md

This becomes your organization's engineering operating system — expressed entirely as intent.

From Intent to Autonomous Engineering

The teambrain-agent/intent.md files point toward the ultimate direction: an AI agent that reads intent files, executes them, monitors results, and iterates — without developer involvement for routine work. Your team's job becomes writing and maintaining intent, not writing code.
